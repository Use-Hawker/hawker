The flow

A paid call is two HTTP requests to the same URL. The first one asks the price, the second one carries the payment.

  1. The agent sends POST /v1/call/:slug with its JSON input and no payment. HAWKER checks the input and answers 402 with the till, the seller, the exact price in USDG units and a fresh call ref.
  2. The agent signs a USDG ReceiveWithAuthorization for that price, made out to the till, and sends the same request again with the signed payment in the X-Payment header.
  3. HAWKER checks the signature, reserves the payment so it cannot be used twice, and simulates the settlement on chain. If the wallet is short, it stops here and nothing runs.
  4. HAWKER runs the call: a house stall in process, a seller's stall by forwarding the request with an HMAC signature.
  5. Only if the stall answered with success does HAWKER send HawkerTill.settle(). The answer is returned once the transaction holds a Paid event for this call.
A failure at any step before the last one costs nothing, and the signature stays valid until its deadline, so the agent can retry with the same one.

The payment

USDG on Robinhood Chain supports EIP-3009, so a payment is a signature, not a transaction. The agent's wallet needs USDG and no ETH.

FieldValue
domain{ name: "Global Dollar", version: "1", chainId: 4663, verifyingContract: USDG }
typeReceiveWithAuthorization(from, to, value, validAfter, validBefore, nonce)
toThe till. receiveWithAuthorization only lets to submit it, so the signature is useless anywhere but the till.
valueThe exact price, in USDG units (6 decimals): 0.02 USDG is 20000.
noncekeccak256(abi.encode(seller, ref)). The seller is part of what was signed, so nobody can send the money to another wallet.
validBeforeA few minutes ahead. HAWKER refuses a payment with less than 20 seconds left.

The X-Payment header is base64 of this JSON:

{ "from": "0x…", "seller": "0x…", "value": "20000", "validAfter": "0",
  "validBefore": "1794318000", "ref": "0x…32 bytes", "signature": "0x…65 bytes" }
USDG answers an authorization whose nonce was already used with success and moves nothing. The till therefore counts what actually arrived and reverts with NotPaid, and HAWKER only trusts the Paid event, never a successful transaction alone.

The listing message

HAWKER stall
slug: weather-now
url: https://api.example.com/weather
price: 0.05 USDG per call
pay to: 0x…
open: yes
at: 1794318000

at is unix seconds within ten minutes of now, and must be newer than the stall's last change, so an old signed listing cannot be replayed.

Errors

Every error is { "error": { "code", "message" } }. None of them charges anything.

bad_signature, bad_payment402Not signed by from, or the header could not be read.

would_not_settle402The wallet does not hold enough USDG.
settle_failed402The stall answered but the payment did not land. No result is returned.

seller_refused4xxThe seller's API turned the input down. Its reply is in sellerReply.
seller_failed, seller_unreachable, stall_failed502The stall could not answer.

Who can do what

WhoCanCannot
The agentSign payments for exact prices to named sellers, within its own limits.Pay more than it signed, or have one signature pay twice.
HAWKER's gatewayChoose not to serve a call. Land a payment it was given.Change the amount, the seller or the buyer of a payment. Hold anyone's USDG.
The till's ownerSet the fee up to 5%, the fee wallet and the holder token.Move a payment, pause the till, or upgrade it. There is no upgrade.
A sellerAnswer calls, and be paid for every 2xx.Be paid without answering: the payment lands only after the answer.

One thing does rest on trust: HAWKER lands the payment after the seller answered and before passing the answer on, so the buyer trusts HAWKER to pass it on, and the seller trusts HAWKER to land the payment. Each payment is a few cents, and every one is on the ledger.
